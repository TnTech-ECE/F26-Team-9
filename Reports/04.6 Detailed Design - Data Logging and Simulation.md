## Function of the Subsystem

This segment should elucidate the role of the subsystem within the entire system, detailing its intended function, aligned with the conceptual design.



The Data Logging and Simulation subsystem, designated Atomic Subsystem 6 in the conceptual design, provides the measurement and analytical foundation for evaluating the proposed Lochinvar variable-speed pump controller. Its role is to collect operating measurements, preserve them in a consistent format, calculate meaningful performance metrics, and develop a simulation that can be compared against the physical heating system. The subsystem is necessary because a controller that changes pump speed cannot be judged successful from the command signal alone. Electrical energy consumption, circulation flow, temperature stability, and the time required to reach the desired temperature must all be considered together.

The subsystem will receive measurements from the Microcontroller and Control Logic subsystem and, when necessary, additional approved measurement equipment. The proposed dataset includes elapsed time, flow rate, inlet and outlet water temperatures, boiler firing rate, pump-speed request, operating state, and fault status. Electrical power should be measured with suitable instrumentation when available; it must not be presented as directly measured if it is only estimated from speed. The data will be stored in files that support later inspection and analysis, allowing baseline pump operation to be compared with the proposed variable-speed strategy under comparable test conditions.

Simulation provides a complementary function by representing the relationships between heating input, circulation flow, temperature response, pump speed, and electrical consumption. A model can be used to examine operating scenarios and controller adjustments before every possible condition is attempted on the physical equipment. The simulation must be calibrated and validated with measurements, because simplified thermal or hydraulic assumptions may not accurately represent the actual boiler and piping. The logging computer is not part of the essential real-time protection loop; failure of the computer or its communication link must not prevent the controller from maintaining its approved protective behavior.

## Specifications and Constraints

This section should provide a list of constraints applicable to the subsystem, along with the rationale behind these limitations. For instance, constraints can stem from physics-based limitations or requirements, subsystem prerequisites, standards, ethical considerations, or socio-economic factors.

The team should set specifications for each subsystem. These specifications may require modifications, which must be authorized by the team. It could be necessary to impose additional constraints as further information becomes available.

Every subsystem must incorporate at least one constraint stemming from standards, ethics, or socio-economic factors.





The subsystem must preserve accurate, time-associated measurements in engineering units. Each record should identify the test, elapsed time or timestamp, flow in gallons per minute, inlet and outlet temperatures, firing-rate percentage, and requested pump-speed command. Controller state and fault codes should be included because they explain changes in operating behavior that may otherwise appear unexplained in a plot. When power is measured using a separate instrument, the records must be synchronized or aligned so that power values correspond to the relevant operating condition. The final sample interval will be selected based on thermal response and communication capacity; it should be justified rather than selected only for convenience.

Data integrity is an important ethical and technical constraint. Invalid messages, missing timestamps, disconnected instruments, and values outside sensor ranges must be identified. Original records should be retained, and any filtering or interpolation should be documented in a separate processed dataset. Measured quantities must be distinguished from estimates and simulation predictions. This distinction is particularly important when presenting energy savings because an idealized pump affinity-law calculation is not equivalent to measured electrical energy reduction. Reproducible analysis requires documented units, consistent formulas, test metadata, and preserved raw data.

The analysis must evaluate the same project constraints as the controller. Outlet temperature will be checked against the ±4°F steady-state target, and minimum flow will be compared with the applicable manufacturer requirement. Time-to-setpoint must be measured using the same criterion for baseline and controlled tests. Electrical performance should be evaluated using both instantaneous power and integrated energy consumption, since variable-speed operation may change throughout a test. Comparisons should use comparable initial temperatures, setpoints, demand conditions, and durations, with any remaining differences explicitly described.

The simulation must represent the dominant thermal and hydraulic behavior without claiming more accuracy than the available data support. A model that matches one steady-state operating point may still perform poorly during startup or load changes. Validation should therefore include more than one operating condition where possible. Practical constraints favor an existing computer and available MATLAB software, while external data acquisition equipment should only be introduced if required measurements cannot be obtained through existing interfaces. The logging equipment must be electrically compatible with the controller and any commercial power meter, and no computer connection should expose a low-voltage USB port to hazardous field voltage.

#### Project Specific Data and Simulation Plan

The proposal identifies a minimum of three operating conditions representing low, medium, and high water demand, subject to the availability of compatible test equipment. Each recorded run should identify which condition is being evaluated, the selected outlet-temperature setpoint, the initial water temperature, the test equipment used, and whether the pump is operating in baseline or controlled mode. This metadata is necessary to compare experiments fairly and to avoid attributing changes in electrical consumption to pump-speed control when the underlying heating demand differs. If the physical system is unavailable, the subsystem may use clearly identified simulated or sponsor-provided data; neither should be reported as a completed laboratory measurement.

The conceptual design names Dymola as a possible simulation tool if sufficient equipment information is available. The simulation scope should therefore be chosen only after the team establishes which thermal capacities, pump curves, flow restrictions, and boiler response characteristics can be obtained or estimated responsibly. MATLAB or Python may be used for plotting and numerical analysis without implying that a Dymola model has already been built. The final report should separate raw observations, derived performance metrics, and model predictions, and should state the uncertainty or limitations associated with each.


## Overview of Proposed Solution

Describe the solution and how it will fulfill the specifications and constraints of this subsystem.



The proposed implementation separates data acquisition, analysis, and simulation into distinct software functions. The team conceptual design identifies Dymola as a possible simulation environment if adequate equipment information is available; therefore, Dymola should remain a conditional candidate rather than being replaced by a claimed finalized MATLAB simulation. MATLAB, Python, or other available software may support data processing and plots. No software environment is treated as purchased or implemented until access and model requirements are verified. A logging program on a computer will open a supported communication connection to the microcontroller and receive formatted measurement records. Each message will be checked for completeness and valid numerical fields before being added to the primary dataset. The program should record connection interruptions and preserve raw messages or error logs so that unexpected gaps can be investigated. The logging process will save measurements incrementally rather than waiting until the end of a long experiment, reducing the amount of information that could be lost during an interruption.

A structured CSV file is proposed for the primary measurement archive. Its columns should include a time field, flow rate, inlet temperature, outlet temperature, firing rate, pump command, operating state, and fault code. If an electrical power meter supplies measurements independently, its readings should be stored with their own timestamps and aligned during processing. The software should also preserve test metadata such as setpoint, baseline or controlled mode, sensor configuration, and relevant operating conditions. Without this information, two data files may look comparable while actually representing different heating loads or measurement setups.

After a test, the data will be imported into MATLAB or another suitable analysis environment. The analysis will compute power savings, electrical energy, temperature error, minimum flow, and time-to-setpoint. Plots will display how these quantities change over time, with baseline and controlled results shown using consistent axes and units. The simulation will use a simplified thermal and hydraulic representation of the equipment, with parameters taken from available manufacturer information and calibrated using measured data. Simulated outlet temperature and flow will then be compared with physical measurements. Model discrepancies will guide parameter adjustments and identify conditions that require additional testing.

The logging and simulation functions will remain outside the real-time safety loop. The computer may stop recording or experience a software error without changing the microcontroller's authority to enforce the approved pump-control constraints. This separation allows data-processing software to evolve without making the heating equipment dependent on a general-purpose computer.



## Interface with Other Subsystems

Provide detailed information about the inputs, outputs, and data transferred to other subsystems. Ensure specificity and thoroughness, clarifying the method of communication and the nature of the data transmitted.



The conceptual design places Monitoring and Performance Evaluation (Subsystem 5) in charge of assessing whether observed water flow, temperature, electrical power, and time-to-setpoint satisfy the project objectives. Data Logging and Simulation (Subsystem 6) supplies organized datasets, graphs, and model outputs to support that evaluation. The interface must therefore permit two forms of input: direct or indirect operating measurements from the sensor/controller chain, and performance results from Subsystem 5 for archival comparison and further analysis. This arrangement is consistent with the project proposal, which states that operating data may arrive through digital communication, stored files, or manual export depending on available hardware. A live USB serial connection is a candidate, not a requirement imposed by the conceptual design.

The primary input is a telemetry stream from the Microcontroller and Control Logic subsystem. The proposed transport is USB serial communication, although the final method must match the selected controller board and available connectors. Each record should have a documented format with a clear start or end boundary, field definitions, units, and an error-handling method. The logger must be able to distinguish a missing record from a legitimate measurement value of zero. A sequence number or monotonic elapsed-time field would make communication gaps easier to identify.

A second possible input is an independent electrical power meter. Because a motor drive may draw nonsinusoidal current, a suitable instrument should measure true electrical power for the selected installation. The meter's data interface must be compatible with the computer or a commercial acquisition module, and electrical isolation must be maintained according to the instrument instructions. The subsystem's outputs are CSV datasets, numerical performance summaries, plots, simulation parameter files, and model-validation results. These outputs are provided to the Monitoring and Performance Evaluation subsystem and used to document whether the controller satisfies its objectives.

## Flowchart

For sections including a software component, produce a chart that demonstrates the decision-making process of the microcontroller. It should provide an overview of the device's function without exhaustive detail.






The flowchart begins with software initialization, recording of test metadata, and opening the communication interface and output file. The program checks whether a measurement record has been received. A missing record triggers a documented gap or reconnection attempt, while a received record is checked for valid structure and numerical fields. Invalid records are flagged and preserved in an error log or raw archive instead of being inserted as valid measurements. Valid records are timestamped and written to the data file.

When the test ends, the software closes and preserves the raw dataset before starting numerical analysis. The analysis stage checks units, timing, and missing values, then calculates electrical energy, temperature error, minimum flow, and time-to-setpoint. The simulation is executed using the documented model parameters, and the predicted outputs are compared with measured data. The final outputs include plots, numerical summaries, model error metrics, and a description of limitations. The flowchart contains decision diamonds for record availability, record validity, and test completion, which makes the software behavior understandable without listing every program statement.

## Analysis

Deliver a full and relevant analysis of the design demonstrating that it should meet the constraints and accomplish the intended function. This analysis should be comprehensive and well articulated for persuasiveness.





#### Project Specific Model Feasibility and Equipment Access

The conceptual design explicitly acknowledges that access to the intended Regent equipment may be limited because available Tennessee Tech laboratory units are shared with other capstone teams. The data subsystem must consequently support a tiered evaluation approach. When a compatible physical system and appropriate sensors are available, the preferred evidence is time-stamped experimental measurements. When the actual Regent is unavailable, the analysis should identify the substitute Lochinvar equipment and describe which characteristics are transferable. When laboratory access or system parameters are insufficient, a simulation may be used for design exploration, but its predictions must be labeled as unvalidated until comparable measured data become available.

The proposal identifies Dymola as a possible model-development environment if sufficient information about the equipment can be obtained. A model can begin with measured flow, inlet/outlet temperatures, heating demand, and pump electrical power where available, then be expanded only as justified by the data. Pump curves, thermal capacity, heat-exchanger dynamics, and the effect of the existing boiler controls are potential unknowns. An unsupported high-fidelity model would create a false sense of precision; therefore, the final simulation should explicitly state its assumptions, input ranges, and unmodeled behavior.

#### Relationship to Performance Evaluation

The Data Logging and Simulation subsystem is not responsible for commanding the circulation pump or replacing the team's Monitoring and Performance Evaluation subsystem. Its main deliverables are organized measurements, reproducible processing, graphs, comparative datasets, and simulation outputs. Performance Evaluation can use those deliverables to assess minimum flow, temperature stability, time-to-setpoint, and energy savings. A clear division of responsibility also reduces the risk that results will be counted twice or that a simulated power estimate will be presented as a measured result.

The first major design decision is to preserve raw data separately from processed results. This improves traceability because filtering, averaging, or interpolation can change the appearance of a measurement record. A reviewer should be able to reconstruct the analysis from the original timestamps and values. The selected CSV format is practical because it can be inspected without specialized software and imported into MATLAB for calculations. Each test must also preserve metadata such as operating mode, temperature setpoint, start condition, and sensor configuration; otherwise, a numerical difference between baseline and controlled tests may be incorrectly attributed to the pump-control algorithm.

Electrical performance should be evaluated using both power and energy. The instantaneous power-savings percentage is 100 × (P_baseline − P_controlled) / P_baseline, provided the measurements represent comparable operating conditions. For a test with discrete power samples, electrical energy in kilowatt-hours is approximated by E_kWh = Σ(P_i Δt_i) / 3,600,000 when power is in watts and time is in seconds. Energy savings are then 100 × (E_baseline − E_controlled) / E_baseline. Integrating power is important because the proposed controller may operate at different speeds throughout the test. A single low-power reading is not sufficient evidence of reduced total electrical consumption.

Thermal performance can be examined using the heat-transfer relationship Q̇ = ṁ c_p (T_out − T_in), where mass flow and specific heat are expressed in consistent units. This equation provides an estimate of the rate of thermal energy transferred to the water, subject to the measurement accuracy and assumptions. Temperature error is defined as e_i = T_setpoint − T_out,i. Mean absolute error is MAE_T = (1/n) Σ|e_i|, but maximum deviation and the percentage of steady-state samples within ±4°F must also be reported. A low average error does not prove that every point satisfied the temperature target. Minimum measured flow is min(Q_1, …, Q_n) and must be compared against the verified manufacturer requirement.

Time-to-setpoint should be calculated using a clearly defined start event and a target-reaching rule applied consistently to baseline and controlled tests. A practical rule may require the temperature to enter and remain within a chosen tolerance band for a specified period, but that criterion must be established before the tests. The simulation will use available pump characteristics, thermal mass estimates, heating input information, and measured response to predict temperature and flow. Its validity should be evaluated using time-aligned measured and simulated series. One useful metric is MAE = (1/n) Σ|y_measured,i − y_simulated,i|, calculated separately for temperature, flow, or other modeled quantities. A model that agrees during steady state should also be checked during changing demand when possible.

Verification begins with a controlled communication test using known telemetry records. The software should be challenged with missing fields, nonnumeric values, interrupted connections, and irregular timestamps. Storage testing must confirm that a file can be reopened and that the saved values match the received measurements. Calculation routines should be checked against hand-calculated examples before actual boiler data are used. During integrated testing, baseline and variable-speed runs should be conducted under comparable conditions, and the analysis should clearly report any differences in load, initial temperature, or test duration.

The principal limitations are the absence of a selected power meter, finalized communication protocol, agreed sampling interval, and experimentally calibrated simulation parameters. Until these are confirmed, the document establishes the analysis method rather than verified performance. The final report should distinguish measured energy savings from model predictions and should avoid projecting annual operating-cost reductions without a justified duty cycle and electricity rate.
